Auth and Onboarding

Status: active · Owner: this plan · Created: 2026-08-23 · Revised: 2026-08-25 · Baseline: main @ 1c2f9d2 · Proof root: docs/proof/auth-and-onboarding/ · Next action: AON10, separate the credential ideas in the console and add the tenants view, so a provider screen never sends a reader to the gateway key page for a provider credential

Outcome

A gateway API key authenticates a request and owns nothing else. A tenant owns API keys, limits, and a credential policy, and a canonical default tenant exists from first boot. Provider credentials have three named sources that the product never blurs: the operator environment, gateway credentials that the operator applies once for the whole deployment, and BYOK, which is only a credential a tenant brings. The operator governs how much of a gateway credential a tenant may spend through that tenant's limits. Authentication is required unless an operator disables it through the CLI, the config, or an admin console switch, and the gateway refuses to serve unauthenticated on a non-loopback address without an explicit second override. A new user starts the gateway, and the CLI opens the console through a one-time launch ticket that becomes a signed session, so the browser never holds the local admin token.

Vocabulary

The campaign fails if these four words stay interchangeable. Every task, route, type, and console label below uses them in exactly this sense.

TermWho owns itWhat it is
Gateway API keya tenantThe STARPORT_ bearer token a client sends to Starport. It authenticates and carries scopes. It is never a provider credential and never a tenant identity.
Environment credentialthe operatorA provider key read from the process environment. Read-only from every HTTP surface.
Gateway credentialthe operatorA provider key the operator applies through the console or the admin API, stored encrypted at scope *, serving the whole deployment. This is not BYOK.
BYOKa tenantA provider key a tenant brings, stored encrypted at scope tenant:<id>, serving only that tenant. This is the only thing the product calls BYOK.

Environment and gateway credentials are both operator credentials. That is the collective noun, and it is why the resolution strategy keeps the name operator_first.

Architecture

The gateway API key keeps its name across both views. The change is that it stops being the tenant identity and stops owning provider credentials. The package that holds provider credentials stops being called byok, because two of the three sources it serves are the operator's.

Scope

Owns: the tenant concept seam and its limits, the three provider credential sources and their HTTP surface, the gateway authentication mode and its CLI, config, and console controls, the local admin token, launch tickets and console sessions, the first-run experience, and the console information architecture for keys, tenants, and provider credentials.

Does not own: catalog acquisition credentials, which Starmap owns; routing policy and price limits, which the OpenRouter parity work closed; and the response cache identity, which reads the tenant value this plan changes but keeps its own contract.

Non-goals: user accounts, passwords, SSO, or OAuth; a hosted or remote control plane; an organization hierarchy above the tenant; per-tenant billing or invoicing; any data migration, because nothing has shipped; and any compatibility alias for a removed route, storage scope, or strategy name.

Invariants

  1. A gateway API key authenticates a request. It never owns a provider credential, and no credential storage key contains an API key ID.
  2. Provider credential resolution order is environment, then gateway scope *, then BYOK scope tenant:<id>. The strategy selects which sources are eligible. It never reorders them.
  3. The word BYOK names a tenant-brought credential and nothing else. No type, route, package, log field, or console label applies it to an environment or gateway credential.
  4. An operator can apply a gateway credential for every provider the catalog knows, without creating a gateway API key and without touching a tenant.
  5. A tenant's limits bound what that tenant spends against a gateway credential. A tenant with no limits inherits no cap; a limit set on a tenant is a ceiling that a key-level limit can lower and never raise.
  6. Authentication is required by default. A build with no configuration serves no unauthenticated inference request.
  7. The gateway refuses to serve with authentication disabled on a non-loopback bind address unless the operator passes a second, explicit override.
  8. The console never receives the local admin token. It receives a one-time launch ticket or a signed session cookie.
  9. Rotating the local admin token invalidates every live console session.
  10. The canonical tenant ID is default. No sample or demonstration tenant ships.
  11. Catalog acquisition credentials stay separate from inference credentials at every seam this plan touches.

Apply it in the budget path and the rate-limit path. 4. Report which level bound the request in the limit response headers and the failure body, so an operator can tell a tenant cap from a key cap. 5. Keep the resolution off the request hot path's storage: read the tenant from the same cached lookup the key read uses. 6. Give usage.Record and usage.Query a tenant dimension. A tenant spend limit cannot bind without one, and AON4 deferred its per-provider rollup here for the same reason: the record is key-indexed today, so nothing can total an account's spend. Serve the rollup at the tenant path once it can.
  • Acceptance: a key with a high limit under a tenant with a low limit is bounded by the tenant, and the failure names the tenant as the binding level. Deleting the default tenant returns 409. The overhead benchmark shows no added storage read per request.

Patterns to preserve

  • Query-string credentials stay unsupported. URLs get logged. The launch ticket is the one exception, and it is single-use and short-lived.
  • Credential material stays encrypted at rest and never appears in a response body, a log line, or an error message.
  • Catalog acquisition credentials stay separate from inference credentials.
  • The 401 and 403 split from the console key work stays intact. A missing key is 401. A key without a scope is 403.
  • Usage records keep the API key ID. The tenant is an added dimension, not a replacement.
  • The gateway adds no measurable request overhead beyond the published budget. Neither the auth mode check nor the tenant limit resolution may add a storage read per request.
  • Provider and model facts keep coming from one Starmap snapshot. The provider credential screens read the catalog's credential fields rather than a local provider table.
