Starport catalog, performance, and brand campaign

Status: active · Owner: this plan · Created: 2026-08-21 · Baseline: main @ 7e71726 · Proof root: proof/catalog-performance/ · Next action: CP11 — Author pages (author list, detail with models and providers)

Outcome

The Starport console presents the catalog as a traversable graph of providers, models, and authors — each with an identity (logo, display name, description) and a full detail page — searchable from a global command palette; the composer follows the industry convention (presets in the model picker, "+" for attachments); every proxied response carries a measured x-starport-overhead-ms header backed by a CI benchmark; the brand reads enterprise-grade (STARPORT wordmark, API Keys, exact metric vocabulary); and the SPA becomes the only console. Design authority: the published Design Review No. 2 (research copies in the proof root).

Architecture

Scope

Owns: the catalog projection seam and its API surface (models, providers, authors, logos); the console catalog UX (provider cards and detail, model detail, author pages, list traversal, command palette); the composer retool; the gateway overhead measurement, header, surfacing, and benchmark; the four gateway defects found in Design Review No. 2; the brand sweep; and the console cutover and cleanup. Also owns the supporting Starmap v0.7.0 release (logo payload, lifecycle dates) in the sibling repository ~/src/github.com/agentstation/starmap.

Does not own: CM0–CM12 (delivered by console-modernization-plan.html, which this plan supersedes once CM12 merges); routing policy changes; new provider integrations.

Non-goals: web-search or deep-research composer tools (no gateway tools path exists; owner: a future tools plan); multi-tenant RBAC; remote catalog hosting changes; marketing site work beyond README claims.

Invariants

  1. Air-gapped console: no CDN or external requests at runtime; logos ship in the binary or the catalog payload.
  2. DESIGN.md governs visual decisions; both themes ship for every surface.
  3. No model, price, or provider facts hardcoded in the frontend; all catalog facts flow from one Starmap snapshot per process.
  4. Provider model IDs stay exact and opaque.
  5. The overhead number is measured, never estimated; the README claim cites the CI benchmark that enforces it.
  6. One task, one pull request to main, branch codex/cp-<n>-<slug>; autoreview pre-PR gate per repository rules.
  7. Do not weaken existing tests or verifier gates to land a task.

Verifier contract

The plan runs it at every task closeout; CP18 wires it into CI once green. Terminal state: 18 passed, 0 failed. Conditions map one-to-one to acceptance criteria named in the tasks below (authors API present, all offerings projected, logo route serves SVG with fallback, provider/model/author routes exist in the SPA, palette indexes three entity kinds, no "+"→presets popover, overhead header on stream and non-stream, TTFT capitalization, STARPORT wordmark, API Keys nav, Starmap pin at v0.7.0 or later). The legacy-console cutover keeps its own gate in scripts/verify-console-modernization.sh; CP18 wires both scripts into CI.

Coordination

console-modernization-plan.html owns work through CM12. When CM12's PR merges, mark that plan superseded(catalog-performance-plan): CM13 maps to CP12, CM14 to CP18, CM15 to CP19. On any disagreement about console scope, this plan wins; on visual tokens, DESIGN.md wins. The published Design Review No. 2 artifact is advisory input; this plan is the execution authority.
