Console Session Grants

Status: active · Owner: this plan · Created: 2026-08-25 · Baseline: main @ 20dd9b1 · Proof root: docs/proof/console-session-grants/ · Next action: CSG9, wire the gate into CI and document the three grants

Outcome

A console session is minted by a named grant, and the grants are a registered set rather than one hard-coded path. Two machine-local grants ship: a one-time launch ticket and the local admin token the reader pastes into a first-contact page. A third grant, an identity provider, ships registered and inert, with a contract test that holds its refusal, so an enterprise deployment adds a provider to an existing route instead of reopening the seam. The words follow the layering: a ticket and a token say where you are, an identity provider says who you are, and only that third grant is allowed to call itself signing in. A reader who starts the gateway and opens the console by hand lands on one page that states its trust scope, takes the token that starport auth token already prints, and offers the exact command that opens the console without a paste.

Vocabulary

TermMeansNever means
Console session The signed HttpOnly cookie that authorizes a console request. Every grant produces this one thing. An account. A session names no tenant.
Grant A named, registered way to mint a console session. Three exist: ticket, local-token, identity. A credential. A grant is the route, not the secret.
Launch ticket A one-time machine-local grant the CLI hands the browser through a URL. A login. It proves reach, not identity.
Local admin token The process-local secret starport auth token prints, usable as a machine-local grant. A gateway API key. It never authenticates an inference request.
Identity grant The registered seam a future identity provider fills. Inert in this plan. A shipped OAuth or OIDC integration.
Sign in Copy reserved for the identity grant. Anything a ticket or a pasted token does.
First contact The page a reader with no session sees, outside the console shell. A card inside the shell. The shell needs a session to render anything true.

Progress

Architecture

The shape of the change is one indirection, not three features. localauth.Gate holds one grant per name and every grant returns through the same IssueSession call, so a new grant cannot invent its own cookie, its own TTL, or its own refusal text. The identity grant is present in that map from the first commit and answers a named refusal, which is what makes its absence a tested state instead of a comment.

Scope

Owns: the grant seam in internal/localauth and its three registrations; the HTTP route that accepts a pasted local admin token; the console first-contact page and the routing that reaches it without the shell; --copy and --open on the auth CLI; the reservation of the words sign in; and scripts/verify-console-session-grants.sh.

Does not own: any OAuth or OIDC provider implementation, a user directory, or a password login — the identity grant ships inert on purpose. Gateway API keys, tenants, provider credentials, and the authentication mode stay as the auth and onboarding campaign left them; scripts/verify-auth-onboarding.sh is terminal at 26 conditions and this plan does not add to it. Remote multi-user session management, session revocation lists, and console SSO are out of scope.

Invariants

  1. Every grant mints a session through one function. No grant builds its own cookie, TTL, or refusal text.
  2. A session records the grant that minted it, so a log line and a test can tell a ticket from a pasted token.
  3. The local admin token and a gateway API key are never accepted at the same field or the same route. A reader who pastes the wrong one is told which one the field wants.
  4. The console never persists the local admin token. It posts the value once and keeps only the session cookie.
  5. The words sign in appear only on the identity grant.
  6. A first-contact surface states its trust scope in the page, not in the documentation.
  7. The identity grant is registered and refuses with a named reason. Its refusal has a contract test.
  8. The pasted-token grant obeys the same exposure rule as token display, read against the caller's address rather than the configured bind: a request that did not come from this machine, presenting an unrotated token, refuses.
  9. A refusal from any grant returns one message for every wrong secret, as launchRefusal already does. Presenting the wrong kind of credential is the one exception: it is a category error rather than a guess, naming it narrows no search space, and leaving a reader to guess which of two credentials a field wants is the confusion this campaign exists to remove.
  10. scripts/verify-auth-onboarding.sh stays at 26 conditions and keeps passing.

CSG1 — The grant seam

Problem. Gate.Redeem is the only path to IssueSession. A second way in has nowhere to attach, so each new one would copy the cookie handling and drift from it.

Owning seam and paths. internal/localauth/gate.go, internal/localauth/grant.go (new), internal/localauth/session.go.

Steps. Add a GrantKind with the three names and a Grant interface whose one method turns a request-supplied secret into a Session or a refusal. Register grants on the Gate by kind. Move ticket redemption behind the ticket registration without changing its behavior. Carry the minting GrantKind in Session and in the signed cookie payload, and reject a cookie whose grant name is unknown.

Acceptance. Ticket redemption keeps its current behavior, proven by the existing launch tests. A session minted by a ticket reports GrantTicket. An unregistered kind refuses rather than panicking.

Fail-before. A test asserting Session.Grant == GrantTicket fails to compile against the baseline.

Verification. go test ./internal/localauth/... ./internal/server/... -race, bash scripts/verify-auth-onboarding.sh still 26 passed, verifier at 4.

CSG2 — The local admin token grant

Problem. starport auth token prints a credential the product accepts nowhere. The console field beside it wants a different credential kind entirely.

Owning seam and paths. internal/localauth/grant_local_token.go (new), internal/localauth/token.go.

Steps. Register a local-token grant that compares the candidate with Token.Authorizes, which already uses subtle.ConstantTimeCompare. Apply the same exposure rule as token display: refuse on a non-loopback bind with an unrotated token. Throttle failed attempts per process with a small fixed delay and a cap, and log a refusal with no secret material. Refuse a value that parses as a gateway API key with the message that names which credential the route wants, so a reader who pastes a STARPORT_… key is not left guessing.

Acceptance. A correct token mints a session reporting GrantLocalToken. A wrong token, an empty value, a rotated token, and a gateway API key each refuse. The exposure refusal fires on a non-loopback bind. Repeated failures are throttled.

Fail-before. Each refusal test fails against a stub grant that accepts everything.

Verification. go test ./internal/localauth/... -race, verifier at 7.

Decisions

IDDecisionReason
D1 The local admin token may cross the browser once, in a form POST, and is never stored there. The auth and onboarding outcome said the browser never holds the token, and a paste field relaxes that. The alternative leaves starport auth token printing a credential nothing accepts, which is the asymmetry this plan exists to close. The half of the property that matters is preserved: no long-lived secret in browser storage, and the session cookie is what persists. Invariant 8 keeps the relaxation loopback-shaped.
D2 Sign in names only the identity grant. A ticket and a token are claims about where you are. Calling either one signing in spends the word a person's identity will need, and teaches a reader that the gateway knows who they are.
D3 The identity grant ships registered and inert rather than absent. A registered grant that refuses with a named reason is testable, and adding a provider later becomes filling a slot. A comment marking a future seam constrains nothing.
D4 Clipboard through the platform command, not a new module. A cgo clipboard dependency would reach the release build of a gateway for one convenience flag. Shelling out costs nothing when unused, and printing on failure keeps the flag honest.
D5 First contact renders outside the console shell. Every shell panel needs a session to say anything true. Shown without one, the navigation leads nowhere and the panels answer 401, which reads as a broken gateway rather than a locked one.

Patterns to preserve

  • launchRefusal: one message for every cause. A refusal that distinguishes an expired ticket from a wrong one is an oracle. The new route copies this exactly.
  • SessionCookies: the HttpOnly session cookie paired with a readable marker that carries no authority. The console tests reach for the marker; nothing may read the session.
  • Token.Authorizes: constant-time comparison stays inside internal/localauth. No caller compares token bytes.
  • AllowsExposure: the rule that governs whether the gateway will show the token also governs whether it will accept it.
