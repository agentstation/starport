Automatic provider runtime

Status: proposed · Owner: this plan · Created: 2026-08-11 · Baseline: main @ b52cd7e286a9a870293155638392ed514b630a47 · Proof root: docs/plans/proof/automatic-provider-runtime/ · Next action: approve activation and start APR0

Outcome

Starport derives every executable provider and its secret-free inference authentication contract from one Starmap generation. It registers those providers without operator credential material. After request policy selects operator or tenant material, Starport binds the catalog endpoint and applies the selected compiled authentication primitive. A reconciler publishes changes through atomic runtime generations and reports scoped provider state. starport dev provides a one-command local start. Production bootstrap stays explicit and fail-closed.

Progress

The status ledger supplies progress.

Architecture

Starmap provides metadata, not credential material. Its credentials.inference plane declares fields, conventional environment names, profiles, primitives, placements, scopes, and endpoint bindings. Starport reads actual material from deployment sources or tenant BYOK. Starport then binds the declared endpoint and applies the selected compiled primitive. Starmap catalog acquisition and Starport inference can read the same environment name independently. They never share resolved material or cache state.

Scope

Owns: provider-neutral bootstrap, local development, catalog-wide registration, credential resolution, endpoint binding, refresh, provider state, admin controls, and first-run docs.

Does not own: new provider transports, new Starmap providers, model identity rules, routing aliases, or catalog acquisition protocols, which require their owning repository or plan.

Non-goals: unauthenticated production, billable startup probes, process environment mutation, provider rosters, local provider authentication tables, model-name inference, or use of acquisition success as inference health. Circuit retuning and new compiled primitives are also outside this plan.

Executable provider: a catalog provider with a non-retired offering, a compiled transport, and a compiled inference authentication primitive, including no-auth. Its endpoint can remain a template until request material binds it.

Invariants

  1. Starmap owns provider IDs, credential fields and environment names, ordered inference profiles, authentication primitives, placements, scopes, endpoint bindings, offerings, endpoints, and model facts.
  2. Starport owns inference credential material, deployment source policy, compiled primitive implementations, provider state, routing, execution, and HTTP protocols.
  3. Provider IDs label state. They never select compiled behavior.
  4. A compiled transport and authentication primitive define the executable boundary.
  5. Operator credentials and tenant BYOK remain separate request policies.
  1. A user_only request never reads operator credential material.
  2. Catalog acquisition credentials never establish inference readiness.
  3. Bootstrap never writes an ambient provider inference credential to disk.
  4. Production never creates a gateway identity or master key implicitly.
  5. A runtime generation changes atomically and drains after request leases end.
  6. Transient source failure retains valid material and the accepted runtime generation.
  1. No warmed inference request contacts a secret store.
  2. An external environment change requires process restart.
  3. Provider state exposes safe reason codes and never exposes credential material.
  4. One failure changes only the scope that provider evidence supports.
  5. Verification uses normal Go scheduling without -p limits.
  1. Gateway readiness reports internal operation while provider state reports inference eligibility.
  2. Inference resolution reads only the Starmap credentials.inference plane, never credentials.catalog_acquisition.
  3. Starmap supplies environment-name and profile order, and Starport adds no provider-specific credential alias or profile table.
  4. Starport attempts a cloud default chain only when a candidate Starmap inference profile declares that compiled primitive.
  5. Starport binds endpoint templates after request policy selects credential material.
  6. A provider-local credential failure cannot block other providers or gateway readiness.

Dependency policy

The audit found no required new dependency because current modules and standard library lifecycle controls cover the planned work. APR0 records the module check. If a task needs a new module, its proof names the missing capability and selected version. It also records license, provenance, maintenance evidence, vulnerability result, runtime closure, and binary effect. Numeric measurements trigger review. They become rejection gates only when an approved product or operational budget defines the limit, owner, consequence, exception path, and reopen condition.

State and failure contract

Adapter support uses ready, unsupported_transport, unsupported_authentication, or no_offerings. Operator credential state uses ready, not_configured, denied, invalid, unavailable, or refreshing. Offering health keeps the existing healthy, open, half_open, and unavailable states, while tenant BYOK stays request-scoped.

An authentication result can invalidate only the exact material version. Broader permission, quota, or billing state requires normalized evidence that proves the scope. Offering circuits handle rate limits, timeouts, and outages, while request errors, cancellation, and unknown failures do not change durable state.
