Document parser

Status: active · Owner: this plan · Created: 2026-08-26 · Baseline: PLG0 pins both repositories · Proof root: docs/proof/document-parser/ · Next action: PLG8 shows the engine, the pages, and the cost in the console

Outcome

A caller attaches a document to a chat request and names a parser plugin. Starport extracts the text in process when the document carries text, and routes a scanned document to an optical character recognition model that Starmap catalogs. The extraction happens once for each document, costs a stated price, and appears in the usage record.

Progress

Progress appears here when the page loads. The status ledger below is the source of truth.

Architecture

The plugin is a request option, not a route. It changes what the model reads, and it never changes which model the router selects.

Scope

Owns, the plugin contract. The decode of the file-parser plugin and its engine vocabulary. The typed refusal for an unknown engine. The rule that ends the unenforced report for the plugins field.

Owns, the extraction path. In-process text extraction for a document that carries text. The optical recognition operation in Starmap, its offerings, and its per-page price. The route from a scanned document to a catalogued recognition model.

Owns, the accounting. The extraction cache keyed by content hash and engine. The page count in the usage record. The price a recognized page draws from Starmap.

Does not own. The document content kind and its wire word, which the model modalities plan owns. Stored file bytes and their retention, which the files API plan owns. That plan closed on 2026-08-27, and its proof stays at docs/proof/files-api/. This plan reads a stored document through that seam rather than build its own.

Non-goals. A layout model that returns bounding boxes, because no caller asks for one. A translation engine, which is a separate operation with a separate price. A parser for a format that no catalogued model reads.

Invariants

IDInvariantReason
P1Starmap owns the recognition operation, its offerings, and its per-page price. Starport adds no local engine table.An engine list inside Starport would restate a catalog fact, and the two would drift at the first provider change.
P2Starport enforces every plugin it accepts, and refuses a plugin it does not enforce.Accepting a field and ignoring it tells a caller that a setting took effect when nothing changed.
P3The native engine runs in the Starport process and reaches no provider.A caller chooses the native engine to avoid a per-page charge, so a hidden provider call would break that choice.
P4One document extracts once for each content hash and engine pair, inside the cache window.A retry, a fallback, and a multi-turn conversation would otherwise pay the page price again for identical bytes.
P5A recognized page records usage and draws a price.An operation that records nothing reads as free, and the spend bound then holds nothing back.
P6A plugin changes what the model reads. It never changes which model the router selects.A request option that moved the route would make the model choice depend on a field the caller set for another reason.
P7The transforms field keeps its current drop-in behavior.The OpenRouter parity surface already ships that behavior, and this plan changes one field rather than the whole option set.

PLG5 The extraction cache

Problem. A conversation resends the same document on every turn, and a retry sends it again. Without a cache, each of those pays the page price for identical bytes. Invariant P4 bounds the work to one extraction for each content hash and engine pair.

Seam. internal/document and its repository.

  1. Hash the document bytes.
  2. Key the cache by the hash, the engine, and the catalog generation. Record the resolved offering inside the entry rather than in the key. The router resolves an offering after planning, and the lookup runs before the paid call, so the generation carries that scope. Any change to the recognition offering set produces a new generation.
  3. Hold the text and the page count in the key store, for a configured window.
  4. Scope an entry to the tenant that paid, and skip it on a fresh request.
  5. Report a cache hit on the response, so a caller can see the saving.

Acceptance, PLG-V12 and PLG-V13. A test asserts that a second request with identical bytes runs no recognition call. A second test asserts that another tenant sharing the same bytes gets its own entry. A third test asserts that a hit records no page cost. A fourth test asserts that a new catalog generation misses the cache.

Fail-before. Two identical requests each call the provider.

Verification. go test ./internal/document/... ./internal/response/cache/.... Then bash scripts/verify-catalog-performance.sh.
