Model modalities

Status: proposed · Owner: this plan · Created: 2026-08-26 · Baseline: starport main at 29a134c, starmap main at ce19e939 · Proof root: docs/proof/model-modalities/ · Next action: MOD0 after approval

Outcome

Starport reaches every model modality that Starmap records as a fact, or Starport names the reason it does not. Starmap states the modalities of each model and the operations of each offering. Starport accepts the matching request, plans a route that serves it, returns the response, and records the cost. Starport drops no content part in silence. No canonical type takes a provider wire word.

Progress

Progress appears here when the page loads. The status ledger below is the source of truth.

Architecture

No seam moves. This plan widens three vocabularies. The content vocabulary lives in internal/inference. The operation vocabulary lives in Starmap. The unit vocabulary lives in internal/usage.

Scope

Owns, the request path. The content vocabulary in internal/inference. The content-part arms of both protocol codecs. The connector adapters that carry a part to a provider. The routing rule that matches a request modality against a model fact. The cache eligibility rule and the request body limit for media.

Owns, the media operations. The Starport routes, scopes, and canonical types for the five media operations. Media units in usage and cost. The console surfaces. One durable verifier.

Owns, in Starmap. The audio token price fields. The five media operation members. The offering derivation that emits them.

Does not own. The catalog data corrections that a new fact-consistency rule demands. Starmap owns those, and they land in the same Starmap pull request as the rule. The OpenRouter parity conditions ORP-V01 through ORP-V16 also stay outside this plan, and decision MOD-D5 states why.

Non-goals. Four items sit outside this plan, and each one now has a named owner. Asynchronous video generation belongs to the async media jobs plan. A files API belongs to the files API plan, which MOD16 promotes and which the async plan then follows. The OpenRouter document parser plugins belong to the document parser plan. Reranking belongs to the reranking plan, which depends on no other plan.

Promotion gate

Promote this plan to active only when every item holds.

  2. The owner approves the six decisions below.

  4. The goal block names real documents, paths, and gates.
  5. The async media jobs plan exists and owns the video non-goal.

MOD4 Modality-aware routing

Problem. Nothing compares the modalities of a request against the modalities of the model. Starport forwards an audio part to a text-only model and reports the provider 400 as its own. Routing policy belongs to Starport, and this rule makes the Starmap modality fact useful.

Two functions in internal/proxy/proxy.go already read the content parts, and both read them narrowly. The first, requestHasVision at line 201, detects ContentImage alone and sets the one capability string that the planner matches. The second, estimatePromptTokens at line 164, counts text and a flat image surcharge alone, so routing sees an audio part and a document part as free. Generalize both here, rather than add a second capability mechanism beside them.

Seam. internal/proxy, internal/routing, internal/router, and internal/catalog.

  1. Project model input modalities onto the route, and derive the request set from its content parts.
  2. Replace the image-only test in requestHasVision with that modality set.
  3. Replace the duplicate estimator in internal/proxy with the internal/tokenize estimator.
  4. Reject a route that does not accept every requested modality.
  5. Apply the same test to every fallback model.
  6. Return a 400 that names the modality when no route qualifies.

Acceptance, MMD-V06 and MMD-V07. A routing test sends an audio part to a text-only model and asserts a 400 that names audio and the model. A second test asserts that the planner drops a fallback model that cannot accept the request. A third test asserts that a model that accepts audio still routes. A fourth test asserts that one estimator serves both the routing metadata and the usage path.

Fail-before. The first test reaches the provider today.
