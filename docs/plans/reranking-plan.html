Reranking

Status: proposed · Owner: this plan · Created: 2026-08-26 · Baseline: RNK0 pins both repositories · Proof root: docs/proof/reranking/ · Next action: RNK0 after approval

Outcome

A caller ranks a list of documents against one query through Starport, on a model that Starmap catalogs. Starport routes the request to a provider that serves the rerank operation, prices the turn from the Starmap price, and counts it against the same limits every other operation obeys. A rerank model never appears as a chat model.

Progress

Progress appears here when the page loads. The status ledger below is the source of truth.

Architecture

No seam is new. Every change lands where the embeddings operation already landed, which gives this plan a working precedent at each step.

Scope

Owns, in Starmap. The third member of ProviderOperation. The rerank endpoint facts. The rerank offerings and their prices. The rule that keeps a rerank model out of the chat completions view.

Owns, in Starport. The canonical rerank request and response. The transport descriptor and the connector adapter. The /v1/rerank route, its codec, and the rerank:write scope. The routing rule that sends a rerank request only to a rerank offering.

Owns, the money path. The search unit in the usage record. The price a rerank turn draws from Starmap. The spend budget that bounds it.

Does not own. The content vocabulary and the media operations. The model modalities plan owns both. A rerank request carries text alone, so this plan and that one share no code and can run in either order.

Non-goals. An OpenRouter rerank route, because OpenRouter serves no rerank endpoint and parity has nothing to match. A vector store or a retrieval pipeline, which rank documents a caller already holds. Reranking inside a chat request, which would hide a priced call inside another one.

RNK-D42026-08-26Price a rerank turn per search unit, which is one query against a bounded document count.The price matches how Cohere bills, so a Starport cost reconciles against a provider invoice. RNK-D62026-08-26Widen the three operation guards before raising the Starmap dependency, and mirror decision MOD-D6 of the model modalities plan.The function planningOperations passes every Starmap operation through, and validateSnapshot then rejects the whole snapshot on one it does not know. RNK-D72026-08-26Refuse a rerank turn on an offering that carries no search-unit price, rather than recording a cost reason.Invariant I5 of the model modalities plan lets a media response carry a recorded cost reason, because a media price is often absent upstream. A rerank price is always present in the catalog, so an absent one means a catalog defect rather than a known gap. The refusal keeps a silent zero out of the spend budget. Re-open if a reachable rerank provider publishes no price.

RNK1 The Starmap rerank operation

Seam. pkg/catalogs in Starmap.

  1. Add ProviderOperationRerank with the wire value rerank.
  2. Accept the member wherever the package validates an operation.
  3. Keep the chat completions view refusing a model that carries the rerank tag.
  4. Add the rerank path and endpoint type, including any author-specific path.
  5. Add a search unit field to ModelOperationPricing, which today names none.
  6. Open one Starmap pull request for this task.

Acceptance, RNK-V01 and RNK-V02. A test asserts that the operation set holds three members and that each decodes from its wire value. A second test asserts that a model carrying the rerank tag stays out of the chat completions view. A third test asserts that every provider with a rerank endpoint names a path.

Fail-before. The constant does not exist, and a catalog that names the operation fails to decode.

Verification. go test ./pkg/catalogs/... in Starmap. Then go build ./....

RNK7 Rerank routing

Problem. The planner builds a route from chat capabilities. A rerank request that reached the chat planner would match a chat model and send a request the provider refuses. Invariant R7 wants that refusal inside Starport, with a message that names the real cause.

Seam. internal/routing and internal/catalog.

  1. Project the operation onto the route candidate, using the named operation set that RNK4 establishes.
  2. Filter candidates to the offerings that serve the operation.
  3. Refuse a model with no rerank offering, before any attempt.
  4. Keep fallback and retry behavior identical to the embeddings path.
  5. Carry the document limit onto the candidate, so RNK5 can enforce it.
  6. Report the refusal with the model identifier and the operation.

Acceptance, RNK-V13 and RNK-V14. A planner test asserts that a chat-only model produces a typed refusal rather than a route. A second test asserts that a model with two rerank offerings produces two ordered candidates. A third test asserts that the refusal message names the operation.

Fail-before. The planner returns a chat candidate for a rerank request.

Verification. go test ./internal/routing/... ./internal/catalog/.... Then bash scripts/verify-dependency-direction.sh.

RNK8 Usage, price, and budget

Seam. internal/usage, internal/limits, and internal/catalog.

  1. Add the search unit count to the usage record.
  2. Compute the count from the query and the document list.
  3. Draw the unit price from the RNK2 offering price.
  4. Add the resulting cost to the tenant spend total.
  5. Refuse a request that would pass the spend bound, before the provider call.
  6. Report the count and the cost on the response usage block.

Acceptance, RNK-V15 to RNK-V17. A test asserts that a recorded turn produces a nonzero search unit count and a nonzero cost. A second test asserts that a tenant at its spend bound receives a refusal before any provider call. A third test asserts that a turn on an unpriced offering fails rather than reporting zero, as decision RNK-D7 requires.

Fail-before. A rerank turn records zero usage.

Verification. go test ./internal/usage/... ./internal/limits/.... Then bash scripts/benchmark-overhead.sh.
