Enterprise readiness campaign

Status: active · Owner: this plan · Created: 2026-08-29 · Baseline: main @ f7dfb6b · Proof root: docs/proof/enterprise-readiness/ · Next action: implement ENR-E1.

Outcome

A Starport deployment answers every operational question an enterprise evaluation asks, without a hosted control plane. The gateway exports its metrics, traces, and usage records to the operator's own systems. It records who changed what. It pushes the events an operator must not poll for. It serves the OpenAI surfaces a 2026 SDK expects: responses, batches, and moderations. Two gateway replicas behind one load balancer share provider health. A configured guardrail refuses what it cannot check. Budgets reach teams. Each capability is a named seam with its own gate condition. The gate scripts/verify-enterprise-readiness.sh is terminal at 33 conditions.

Progress

Progress appears here when the page loads. The status ledger below is the source of truth.

Architecture

The campaign adds five seams: internal/telemetry, internal/events, internal/audit, internal/guardrails, and internal/mcp. It moves availability state from a per-process map to shared KV state when the operator configures Valkey. Names stay identical across both views.

Scope

Owns: the export plane (Prometheus metrics, OTel traces, usage sinks). The governance plane (audit log, webhooks, the security posture document). OpenAI surface parity (/v1/responses, /v1/batches, /v1/moderations). Routing spread and shared provider health. The guardrail seam with two built-in checks. Team budgets, semantic caching, preset revisions, the MCP server, and the IDENTITY-001 repair.

Does not own: the Starmap catalog facts a task needs. The moderations operation and its offerings land in the starmap repository first. ENR-D2 names that dependency. Payments, credits, and billing rails belong to no plan. Starport positions against the hosted marketplace, not toward it.

Non-goals: a hosted control plane. SOC 2 certification itself, because ENR-C3 ships the evidence document only. An organization tier above accounts, which ENR-G2 defers with a recorded re-open condition. Provider-side batch passthrough: the gateway executes batches itself, so a batch works on every provider.

Invariants

  1. scripts/benchmark-overhead.sh stays green on every task. A disabled feature adds no measurable per-request cost.
  2. Passive surfaces, such as the /metrics endpoint, may default on. Active exporters stay off until configuration names them: OTLP, usage sinks, webhooks, and guardrail model calls. starport dev keeps its stateless-disk contract and sends no outbound telemetry.
  3. Starmap owns provider, model, offering, and operation facts. No task adds a local model list, price default, or provider switch.
  4. No export surface carries a provider credential, gateway key material, or prompt and response content. Export surfaces are metrics, traces, usage sinks, audit records, and webhook payloads. The one exception is a sink that configuration names as content-carrying.
  5. Existing gates keep their terminal counts. The counts are AON 26, CSG 16, MMD 26, FIL 22, AMJ 18, PLG 20, RNK 22, CSH 23, ORP 17, and CDP 19.
  6. A configured guardrail that cannot evaluate refuses the request. Fail closed, never fail open.
  7. Deterministic routing stays the default. Spread is opt-in per request or preset.

Rejected designs

  • Organization tier above accounts. Rejected for now. The identity plane covers every deployment seen so far with users, teams, memberships, and account grants. An organization layer would touch identity, limits, grants, and the console on speculation. Re-open when a real operator needs several isolated account sets under one deployment. ENR-G2 holds the deferral.
  • Provider-native batch passthrough. Rejected. Each provider's batch API differs in format, polling, and pricing. A passthrough would leak provider job identifiers that the AMJ campaign hides on purpose. The gateway executes batches through its own planner instead. Re-open if a provider's batch discount becomes decisive for a real deployment.
  • Always-on content logging. Rejected. Prompt and response content leaves the process only when a configured sink names content explicitly, per invariant 4.
