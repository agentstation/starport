## 1. `agentstation/modelwiki` — what it actually is

`/Users/jack/src/github.com/agentstation/modelwiki` is a **Go CLI + Hugo static-site generator**, not a web app. It reads a Starmap catalog (`github.com/agentstation/starmap/pkg/catalogs`) and emits Markdown into `docs/`, which Hugo renders with the `hugo-book` theme. There is no React, no component library, no interactive UI. Its value to Starport is **information architecture and the logo pipeline**, not code.

**Three-way taxonomy** (the same one Starport needs): `docs/providers/<id>/`, `docs/authors/<id>/`, and models nested under their *author* at `docs/authors/<author>/models/<model-id>.md`. Models live under the author, and providers link to them — so a model has one canonical page and N provider offerings. That is exactly the Starmap ownership model.

**Page IA, from the generated output:**

- **Provider page** (`docs/providers/anthropic/_index.md`, generated by `internal/generator/docs/provider.go`, 32KB): logo + name heading, then `Provider Information` (ID, model count, auth type, env var, status page), `API Endpoints`, `Privacy & Data Handling`, `Data Retention Policy`, `Content Moderation`, `Headquarters`, `Available Models` grouped by family with a Context/Input/Output/Features table, `Configuration`, `See Also`. The privacy/retention/moderation trio is unusual and genuinely useful for a gateway operator picking a route.
- **Author page** (`internal/generator/docs/author.go`): `Organization Information`, `Models`, `Provider Availability`, `Research & Development`, `See Also`. "Provider Availability" is the key cross-link — which providers serve this author's models.
- **Model page** (`internal/generator/docs/model.go`): `Technical Specifications`, `Capabilities`, `Provider Availability`, `Related Resources`, `Other Models by This Author`.

**The reusable gem is `internal/generator/docs/badges.go`** (14KB). It enumerates 50+ model features and — critically — **tiers them as `core` / `advanced` / `niche`** with a color and a tooltip each: modality badges, tool badges (`tool_calls`, `tools`, `tool_choice`, `web_search`, `attachments`), reasoning badges (`reasoning_effort`, `reasoning_tokens`, `include_reasoning`, `verbosity`), generation controls (`temperature` core, `top_k` advanced, `no_repeat_ngram` niche), and delivery badges. That tiering is a ready-made progressive-disclosure spec for a model detail page: show core inline, advanced behind a disclosure, niche in a "full spec" table.

**Logo pipeline:** `internal/generator/docs/logo_copier.go` copies SVGs out of the Starmap source tree at `<starmap>/internal/embedded/catalog/{providers,authors}/<id>/logo.svg` into `docs/assets/logos/{providers,authors}/<id>.svg`, warning rather than failing on a miss. `internal/generator/docs/logo.go` additionally reads from an `embed.FS` and falls back across `.svg/.png/.jpg/.jpeg/.webp`. **Starmap already ships per-provider and per-author logos** — 23 in modelwiki's copy today (15 authors, 8 providers). That is Starport's logo source of truth and it needs no CDN. Caveat: the *generated* provider pages hotlink logos to `raw.githubusercontent.com/agentstation/starmap/master/...`, which would break air-gapped; the copier path is the correct one to follow.

## 2. Ranked exemplars

### #1 — `agentgateway/agentgateway/ui` (React + Vite + TanStack Router)

Path: `/Users/jack/src/github.com/agentgateway/agentgateway/ui`. Deliberately lean: React, TanStack Router + Query, lucide-react, Monaco (YAML config editing), recharts, zod. **No Tailwind and no shadcn** — it uses hand-written CSS classes (`page-stack`, `panel`, `table-wrap`) and its own primitives in `src/components/Primitives.tsx` (945 lines: `PageHeader`, `Panel`, `Drawer`, `EmptyState`, `Field`, `StatusBanner`, `Tooltip`, `YamlBlock`). A gateway console can be excellent without a component framework.

Four patterns worth taking:

**Bundled provider logos with a mono/color split.** `src/components/ProviderIcon.tsx` statically imports 21 SVGs from `src/assets/providers/` into a `Record<string, string>`, so Vite fingerprints them into the bundle — zero network. It keeps a `monochromeProviders` Set (openai, anthropic, xai, ollama…) that applies a `provider-icon-mono` class so single-color marks get tinted to the theme while colorful marks pass through. The fallback is `providerInitials()` — two-letter initials in a bordered circle, with a hardcoded `xAI → "xA"` special case. Starport should copy this shape but drive the map from the Starmap catalog rather than 21 hand-written imports.

**Nav that hides sections the config does not use.** `src/components/Shell.tsx:214` `navigationGroups({hasLlm, hasMcp, hasTraffic, dumpMode})` returns grouped items, and when `llm` is absent the group collapses to a single "Get started" placeholder. The LLM group's order is instructive for Starport: Models, Providers → Policies, Guardrails, Virtual API Keys, Costs → Analytics, Logs → Client Setup, Chat Playground. `groupStart: true` inserts a visual rule between sub-groups.

**Deep-linkable detail drawers.** `src/pages/Providers.tsx` uses `useStickyQueryParam("provider")` from `src/drawerRouteState.ts`: the list is a table, and clicking a row opens a `Drawer` while writing `?provider=<name>` to the URL, with `"new"` as a sentinel for the create flow. The URL is the state, so detail views are shareable and back/forward work. `src/pages/models/modelRouteState.ts` does the same for models.

**Freeform-but-guided model selection.** `src/components/CatalogModelSelector.tsx` + `FreeformCombobox.tsx`: the combobox suggests models from the live cost catalog filtered to the selected provider, but accepts any typed string, with empty-state copy "No catalog matches. Custom model names are allowed." It also carries a provider-alias map (`bedrock → aws.bedrock`, `vertex → gcp.vertex_ai`). Starport should never need the alias map — Starmap owns the IDs — but the "suggest from catalog, allow opaque" behavior matches Starport's rule that provider model IDs stay exact and opaque.

**Serving:** `crates/agentgateway/src/ui.rs:47` embeds `ui/out` with `include_dir!` and mounts it at `/ui` via `nest_service`, with `/` redirecting there and the API under `/api/*`. Vite's `base` is set to `/ui/` for builds. Direct precedent for Starport's Go `embed.FS`.

Weak spots: `src/pages/Models.tsx` is 1,902 lines and `Logs.tsx` 1,922 — past the 2,000-line decomposition threshold in your global rules. Read them for IA, not for structure.

### #5 — `pomerium/pomerium/proxy/portal` (Go, embedded logos)

Path: `/Users/jack/src/github.com/pomerium/pomerium/proxy/portal`. Not a React exemplar — an **architectural** one, and the only Go-native logo-serving precedent in the tree. `logo_provider.go` defines a `LogoProvider` interface with a `multiLogoProvider` chain that walks providers and skips on `ErrLogoNotFound`. `logo_provider_well_known.go` embeds 36 SVG/PNG files one-by-one with individual `//go:embed logos/<name>.svg` directives and returns them as **base64 `data:` URLs** (`dataURL(mediaTypeSVG, kafkaLogo)`), keyed by port number. `logo_provider_favicon.go` is the network-fetching tier — the one Starport would omit.

The data-URL return is the interesting choice: logos arrive inside the JSON API response, so the UI needs no second request and no separate asset route. For ~30 provider marks that is a reasonable trade; for hundreds it is not, and a `/console/assets/logos/<id>.svg` route off an `embed.FS` is better.

## 3. Concrete recommendations for Starport

**Logo strategy.** Take Starmap's existing `internal/embedded/catalog/{providers,authors}/<id>/logo.svg` set, mirror modelwiki's copier (`internal/generator/docs/logo_copier.go`) as a build step or an `embed.FS` in the console package, and serve it from the gateway at a stable path. Follow clawpatrol's shape — `/Users/jack/src/github.com/denoland/clawpatrol/dashboard/embed.go` is a nicely commented `//go:embed all:dist` + `fs.Sub(DistFS, "dist")` + `http.FileServer` at `cmd/clawpatrol/web.go:981`, with the SPA and its assets in one embedded tree. Layer agentgateway's mono-vs-color classification and initials fallback on top, since Starmap logos will have gaps. Note Starmap's set is small (8 providers, 15 authors in modelwiki's copy) — for anything missing, the local harvest options are `agentgateway/ui/src/assets/providers/` (21 LLM-specific SVGs, the highest-precision set available), `onecli/onecli/apps/web/public/icons/` (85 brand SVGs **with `-light` variants**, best dual-theme set), and `nimbus/nimbus/website/node_modules/simple-icons/icons/` (3,442 CC0 icons including `anthropic`, `claude`, `mistralai`) as a last-resort fallback.

**Catalog IA.** Adopt modelwiki's provider / author / model triangle verbatim — it is already the Starmap ownership model, so the console mirrors the domain rather than inventing a second one. Provider pages carry Starport-owned facts (credential status, availability, circuit state, rate limits) alongside Starmap-owned facts (endpoints, privacy, retention, model list); author pages carry the cross-provider "which of my models can this gateway reach" view; model pages carry the spec plus a provider-availability table, which for Starport doubles as the routing preview.

**Model detail progressive disclosure.** Use `badges.go`'s core/advanced/niche tiering as the spec. Core capabilities as icon chips in the card row (Jan's `Capabilities.tsx`), advanced behind a disclosure, niche in a full-spec table.

**Search and traversal.** Jan's stack is the right one at catalog scale: `@tanstack/react-virtual` + Fuse.js on a small key set + 300ms debounce inside `useTransition`, with facets as explicit controls (sort dropdown + toggle switches) rather than a filter sidebar. Add a command palette later — Daytona has one at `/Users/jack/src/github.com/daytonaio/daytona/apps/dashboard/src/components/CommandPalette.tsx`.

**Detail views.** Deep-linkable drawers over separate pages for editable config (agentgateway's `useStickyQueryParam`), full routes for browsable catalog entries (Jan's `/hub/$modelId`). Convex's `DetailPanel.tsx` is the better slide-over implementation if you are on Headless UI or Radix.

**One thing nobody local does well:** none of these consoles has a strong provider *card* grid — agentgateway uses tables, Jan uses settings rows, Lunar's cards are for MCP servers. If Starport wants provider cards with logo, health, latency, and cost at a glance, that design is not sitting in this tree and will need to come from the design-research thread.
