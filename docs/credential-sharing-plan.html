Credential sharing and identity

Status: active · Owner: this plan · Created: 2026-08-29 · Baseline: main @ b00c47d · Proof root: docs/proof/credential-sharing/ · Next action: CSH-C3 ship the shared credential console list UI

Outcome

An operator runs Starport for an organization, not one person: each provider can hold many shared credentials, each shared credential is open to every account or granted to some, each account carries an operator-set BYOK policy and its own provider and model access, an operator creates accounts from templates, and people sign in through OAuth (gothic) or enterprise SSO (WorkOS) as users on teams whose grants decide which accounts they reach. Relational state lives in an embedded SQLite database inside the binary, with PostgreSQL or MySQL as the scaling connect, exactly as Badger pairs with Valkey.

Progress

Progress appears here when the page loads. The status ledger below is the source of truth.

Architecture

The new seams: internal/sqlstore owns the relational contract with an embedded SQLite backend and a PostgreSQL/MySQL connect, mirroring how internal/storage pairs Badger with Valkey. internal/identity owns users, teams, and account grants, and activates the inert identity grant in internal/localauth. internal/providers/keyring grows from one gateway credential per provider to a list of shared credentials, each open or granted.

Scope

Owns: the credentials-section console redesign landing; the relational store seam (embedded SQLite default, PostgreSQL/MySQL connect); multiple shared provider credentials with per-credential open-or-granted access; the operator BYOK policy and account provider/model access; operator account templates; OAuth identity through gothic and enterprise SSO through WorkOS; users, teams, and account grants; the console surfaces, routes, gates, and docs for all of it.

Does not own: provider and model catalog facts (Starmap owns them); model routing presets at /presets (existing concept, untouched); the down health word, which waits on provider-status-page integration (future work, no plan yet).

Non-goals: billing or invoicing per account; SCIM or directory sync beyond what WorkOS SSO returns; migration or compatibility paths for pre-release storage shapes — breaking changes land directly per CLAUDE.md.

Standing decisions

  1. Wire and keyring rename folds into CSH-C1. The earlier console-only vocabulary decision deferred renaming the stored credential's wire and keyring word gateway. CSH-C1 rebuilds that storage and wire shape anyway, so the rename to shared rides the same breaking change. The user may veto before CSH-C1 starts.
  2. Account templates, not presets. The console and wire word for operator account-creation defaults is template, because preset already names model routing presets at /presets.
  3. Per-credential access choice at creation. The create flow asks whether a shared credential serves every account or only granted ones. The default is open to every account.
  4. Identity is optional. A deployment with no OAuth or SSO configured behaves exactly as today: launch tickets and the local admin token mint console sessions, and accounts work with no users attached.
  5. SQLite rides the binary. The SQLite driver is pure Go (no cgo) so the single-binary install story holds.
  6. The identity name goes to humans. internal/identity holds gateway API-key identity at baseline. That package renames to internal/apikey in CSH-F1 (mechanical, pre-release direct breaking change), so the human seam — users, teams, memberships, grants — takes the name the localauth identity grant already uses.

Invariants

  1. A gateway API key authenticates a caller and never pays a provider. The AON gate stays green at every step.
  2. internal/providers/keyring alone owns the credential source words. Resolution order stays environment, then shared stored, then the account's own, subject to strategy.
  3. No legacy names, storage prefixes, or compatibility paths. Pre-release breaking changes land directly.
  4. No route returns a stored secret, and no tool output prints one.
  5. Badger stays the default KV store and SQLite becomes the default relational store. A deployment scales to Valkey and PostgreSQL/MySQL through configuration alone.
  6. The words sign in stay reserved for the identity grant. The CSG gate is revised consciously in CSH-F2, never loosened as a side effect.
  7. Every gate in CLAUDE.md's required evidence list is green before each pull request, plus scripts/verify-credential-sharing.sh once CSH-A0 lands.
